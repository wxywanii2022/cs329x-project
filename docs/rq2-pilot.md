# RQ2 live pilot: models, run and review

Purpose: run the whole simulator once with real models, check that the learner
behaves plausibly for its profile, and decide whether the learner (or task) prompts
need changes before any held-out run. This is a development pilot on development
tasks. Its numbers are not effect estimates.

## Roles and models (decided 2026-11-21)

Every role runs locally under vLLM 0.32 on one FarmShare node (4x L40S 48 GB), one GPU
per role, each server on 127.0.0.1 only. No API keys are used. Learner, coach and
evaluator are distinct families from distinct labs. None of them is Qwen, because the
coach reads the Qwen assessor's labels.

| Role | Model (pinned revision in `configs/rq2-pilot/pilot.json`) | Lab | Adapter and decoding |
| --- | --- | --- | --- |
| Assessor | Qwen/Qwen3.8-27B-FP8, frozen v2 (unchanged from `configs/live.example.json`) | Alibaba | `local_vllm`, thinking on, RQ1 flags |
| Learner | google/gemma-4-31B-it-qat-w4a16-ct (Google's own 4-bit QAT checkpoint) | Google | `local_chat --schema utterance`, thinking off, T 1.0 / top-p 0.95 / top-k 64 (model defaults) |
| Coach | mistralai/Ministral-3-14B-Instruct-2512 (FP8) | Mistral AI | `local_chat --schema decision`, T 0.05 (vendor: "below 0.1") |
| Evaluator | openai/gpt-oss-20b | OpenAI | `local_chat --schema annotation`, reasoning effort high, T 1.0 / top-p 1.0 |

Why these models: the simulator guide asks for the learner to be chosen for fidelity,
the coach for instruction following and the evaluator for agreement with human labels.
Each model also had to fit on one 48 GB GPU and come from an ungated repo, since there
is no HF token on the cluster. Gemma 4 31B is the strongest non-Qwen dense chat model
that fits, and it runs with thinking off so its turns read like a person replying.
Ministral 3 14B only has to pick one bank exercise or none, in JSON. gpt-oss-20b is the
strongest non-Qwen reasoning model that fits on one GPU. Meta has no current open model
that fits on one GPU (Llama 4 is too large). Nemotron was avoided because NVIDIA's
published post-training datasets include synthetic data generated by Qwen models,
which would weaken the separation from the assessor.

The evaluator is **not yet validated against human labels**. The pilot runs it only on
the 13 constructed v0.2 fixtures. Before research runs it needs the same kind of human
comparison the assessor had (for example on Main 2, which lives on the SC cluster), with
the model pre-declared and not chosen on that data.

`adapters/local_chat.py` serves the three non-assessor roles. It reuses
`local_vllm.py`'s loopback rule, annotation schema and envelope by import. It does not
edit that file, because `local_vllm.py` is hashed in the RQ1 preregistrations. The JSON
schema only constrains the shape of the output, and the runner's validators still decide
acceptance. For the coach, the schema allows only "none" or an (exercise, behavior) pair
that exists in the bank.

## Pilot design

`configs/rq2-pilot/pilot.json`: 6 profiles x {briefs_01, accurate_01} x AB/BA x 2
replicates = 48 blocks (48 uncoached pre-tasks, 4 per profile per pair; 192 branches;
240 scored records). `scripts/rq2_pilot.sbatch` runs these stages:

1. Start four servers and wait until each is healthy (any startup failure stops the job).
2. Smoke: one full block (novice_a, briefs_01, AB). Any failed branch or score stops the
   job before the pilot. In parallel, it runs the frozen v2 assessor and the evaluator on
   `data/rq2/v02_fixtures`. v2 has not been run on the fixtures before; v3 has, in
   `outputs/rq1-v3`.
3. Pilot: one shard per profile x pair (12 runs) in parallel against the same servers.
4. Audit every run and write `outputs/rq2-pilot/report.md`, `report.json` and
   `transcripts/<profile>.md`.

```bash
mkdir -p outputs/logs && sbatch scripts/rq2_pilot.sbatch
# resume after a time limit or crash: the same command
python3 scripts/rq2_pilot_report.py outputs/rq2-pilot   # re-create the report anywhere
```

Storage: the three new models are downloaded to `/scratch/users/$USER/hf/hub`, and vLLM,
Triton and pip caches go to `/scratch/users/$USER/cache`. The frozen Qwen weights stay
in `~/.cache/huggingface`. Nothing new and large goes into `$HOME`.

## What to review

The report is a set of pointers; the transcripts are the evidence. For each profile:

- **Request turn (B1/B2):** does the learner state deliverable or evidence requirements
  at a rate that fits the profile? Does it invent figures it cannot know (flag
  `invented_figure_at_request`)?
- **Review turn (B3):** with the numbers visible in the draft (100 -> 128, "35%"),
  does every profile catch the error at once? If novices compute 28% as reliably as
  experts, the learner is too competent for its profile. That is the most likely
  prompt problem, and it is the main thing this pilot checks.
- **Accurate pair:** false alarms on a correct draft.
- **Voice:** `meta_leak` (talks about its profile, misconceptions, JSON or stages),
  `assistant_voice`, `long_message`, and near-identical requests across replicates
  (request similarity).
- **Coaching:** does the learner engage with practice, decline it, or comply too
  readily? Does the coach choose "none" for learners with no visible gap?
- **Task agent:** the scripted agent reacts to lexical patterns (`tasks.py`). Look for
  learner turns that clearly check or correct but are not recognized ("discovery" is
  prompted, or B4 is scored at the correction turn). Those cases call for task-agent
  changes, not learner-prompt changes.

Change prompts only after reading transcripts, and record every change as a new prompt
version in a new output directory.
